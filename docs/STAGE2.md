# Этап 2: режимы sandbox / local, политика, подтверждения, аудит

Всё это один плагин: `plugins/ferrum` (TypeScript, загружается движком как есть, без форка ядра). Конфиг: `config/ferrum.baseline.json5`.

## Что делает

| Что | Как |
| --- | --- |
| Два режима на сессию | по умолчанию **sandbox** (Docker, этап 1). `/mode local` переключает сессию в **local**. Состояние хранится в памяти шлюза: после перезапуска шлюза всё снова sandbox. |
| Включение local | `/mode local` → бот присылает 4-значный код → `/mode confirm <код>`. Код действует 60 с, привязан к сессии, одна неверная попытка сжигает его. Команда доступна только владельцу (`commands.ownerAllowFrom`) и работает до того, как сообщение увидит модель, так что модель не может включить local сама. |
| Выход из local | `/mode sandbox` (сразу) или автоматически после **10 минут** без обращений к `local_*`. `/mode` без аргументов показывает текущий режим. |
| Доступ к ПК | только пять инструментов `local_read`, `local_list`, `local_write`, `local_delete`, `local_exec`. В режиме sandbox они **не регистрируются** (модель их не видит), а вызов по имени блокируется хуком `before_tool_call`. Подагенты, cron, hook, ACP-сессии в local войти не могут. |
| Область | `D:\Ferrum` (параметр `localRoot`; в WSL это `/mnt/d/Ferrum`, параметр `localRootMount`). Всё остальное отклоняется. |
| Подтверждения | через штатный `requireApproval` движка: кнопки в Telegram (`allow-once` / `deny`), текст запроса показывает **всю** команду целиком. Без подтверждения вызов не выполняется (fail-closed, в том числе если подтвердить негде). |
| Аудит | `~/.ferrum/audit/YYYY-MM-DD.jsonl` (каталог 700, файлы 600, вне workspace и вне песочницы): каждый вызов инструмента (любого, не только `local_*`) с решением, результат, подтверждения, смены режима, отказы. Секреты вырезаются (`audit.ts`). |

### Правила для инструментов local

| Действие | Решение |
| --- | --- |
| `local_read`, `local_list` внутри `D:\Ferrum` | сразу, без вопросов |
| `local_write` нового файла внутри `D:\Ferrum` | сразу |
| `local_write` поверх существующего файла | подтверждение владельца |
| `local_delete` | всегда подтверждение; корень удалять нельзя |
| `local_exec` | всегда подтверждение (команда ≤ 400 символов, PowerShell, таймаут 120 с, рабочая папка `D:\Ferrum`) |
| Любой путь вне области, UNC, `\\?\`, `\\wsl$`, `C:`, `..`, потоки `a:b`, зарезервированные имена (`CON`, `NUL`…), короткие имена `PROGRA~1`, символические ссылки | отказ |
| `*.vhdx`, `*.vhd`, `$RECYCLE.BIN`, `System Volume Information` | отказ |

Команда `local_exec` дополнительно отклоняется, если содержит: закодированные команды и base64, `Invoke-Expression`, `wsl`, UNC-пути, `..`, `$env:`/`%VAR%`/`~`, работу с дисками, реестр, службы и планировщик, `RunAs`, выключение, `.ssh`/`.openclaw`/`.aws`/`.kube`, пути с буквой диска вне области. PowerShell запускается из WSL с окружением из одного `PATH`: переменные шлюза (токены, ключи) в него не попадают. При таймауте или отмене процесс и его потомки убиваются через `taskkill /T /F`.

Сетевые команды (`curl`, `Invoke-WebRequest`…) жёстко **не** запрещены: любая команда `local_exec` и так требует подтверждения, и ты видишь её целиком. Так решено осознанно.

### Лимиты

- Число вызовов инструментов за ход **не ограничено** (`maxToolCallsPerTurn: null`). Ограничитель есть в плагине: задай число в `plugins.entries.ferrum.config.maxToolCallsPerTurn`.
- Время одного хода: `agents.defaults.timeoutSeconds: 600` (штатно).
- Штатная защита от зацикливания: `tools.loopDetection.enabled: true`.
- **Лимит 200 тысяч токенов на ход не реализован**: в публичном API движка нет хука с учётом токенов в ходе, дешёвого способа нет. Страхуют таймаут хода и обнаружение циклов. Если нужен жёсткий лимит, это отдельная работа (возможно, потребует правки ядра, спрошу заранее).

**Не проверено вживую** (проверь вручную по списку ниже):

1. Команда `/mode` из настоящего Telegram. В тестах CLI не считается авторизованным отправителем (`requireAuth`), поэтому через `chat.send` команду не вызвать; обработчик проверен юнит-тестами с поддельным контекстом.
2. Кнопки подтверждения в Telegram для плагинных запросов (`plugin:…`). По документации движка они идут через `channels.telegram.execApprovals`. Если кнопок нет, запасной вариант: добавить в конфиг `approvals.plugin: { enabled: true, mode: "session" }`; текстовая команда `/approve <id> allow-once` работает в том же чате.
3. Настоящий `powershell.exe` из WSL и доступ к `/mnt/d/Ferrum`. Интероп у тебя работает (проверено `powershell.exe` → `ok`), но сами `local_*` не запускались на Windows.
4. Реальная модель.

## Ограничения (честно)

- **Эвристики `local_exec` обходимы** (PowerShell слишком выразителен). Настоящая граница: ты читаешь точную команду и жмёшь «Подтвердить». Не подтверждай то, чего не понимаешь.
- **Junction в `D:\Ferrum` не видны** из WSL как ссылки, поэтому не обнаруживаются (символические ссылки обнаруживаются и отклоняются). Не создавай junction внутри `D:\Ferrum`.
- **`*.vhdx`**: если диск WSL лежит внутри `D:\Ferrum`, это недопустимо. Файлы `.vhdx`/`.vhd` через `local_*` отклоняются, но держи диск WSL вне области (например `D:\WSL\Ubuntu`).
- Режим local хранится в памяти шлюза: перезапуск шлюза возвращает sandbox (безопасная сторона).
- Подтверждение действует на один вызов (`allow-once`), «всегда разрешать» не предлагается.
- Права `D:\Ferrum` в Windows плагин не меняет: программа, запущенная через `local_exec` после твоего подтверждения, делает всё, что может твой пользователь Windows в этой папке и вне её (поэтому подтверждение, а не фильтр, является границей).

## Как запустить проверки

```bash
export PATH=/tmp/n24/node_modules/.bin:$PATH   # если Node 24 не системный
npm test                         # контрактные тесты + юнит-тесты плагина (без сети и Docker)
npm run test:plugin:integration  # настоящий шлюз с поддельной моделью (~50 с); --verbose, --keep
npm run test:isolation           # настоящий Docker (этап 1, теперь с загруженным плагином ferrum)
```

## Включение на твоей машине

1. `git pull`, затем `ferrum setup` (или `bash scripts/wsl/40-configure.sh`, это то же самое) заново: он добавит в `~/.openclaw/.env` строку `FERRUM_REPO` (путь к пакету) и обновит конфиг (старый сохранит рядом). После этого `ferrum doctor`.
2. Создай папку `D:\Ferrum` (если её нет) и убедись, что в WSL виден `/mnt/d/Ferrum`.
3. Перезапусти шлюз (`ferrum start`). В логе должна быть строка про загрузку плагинов `ferrum`.

## Ручная проверка в Telegram (по порядку)

1. `/mode` → «Режим: SANDBOX».
2. Попроси: «прочитай файл D:\Ferrum\a.txt» → агент не должен получить доступ (инструментов нет), ответит, что нужен local.
3. `/mode local` → пришёл код; `/mode confirm 0000` (неверный) → «Не включено»; снова `/mode local` и `/mode confirm <код>` → «Режим: LOCAL».
4. «Создай файл D:\Ferrum\hello.txt с текстом привет» → создан без вопросов. Файл появился на Windows.
5. «Перезапиши hello.txt» → приходит запрос подтверждения с кнопками. Нажми «Отклонить»: файл не изменился. Повтори и подтверди: изменился.
6. «Удали hello.txt» → запрос; подтверди.
7. «Выполни Get-Date» → запрос с полным текстом команды; подтверди; пришёл результат.
8. «Прочитай C:\Windows\win.ini» и «выполни Get-Content ..\..\x» → отказ без запроса.
9. Подожди 10 минут без обращений → `/mode` показывает SANDBOX; `local_*` снова не работают.
10. `~/.ferrum/audit/<сегодня>.jsonl` содержит всё вышеперечисленное, без токенов.

Если на шаге 3 команда не срабатывает, а сообщение уходит модели, пришли строку из лога шлюза и вывод `ferrum engine config get commands.ownerAllowFrom`.
